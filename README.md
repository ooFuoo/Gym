# Gym 前端项目

这是一个使用 React 19、TypeScript 6 和 Vite 8 搭建的前端项目。目前处于基础工程阶段，页面仍为 Vite 起始页，包含一个用于验证交互和热更新的本地计数器。业务目标和 Part 5 的完整需求尚未提供，因此本文会明确区分已有实现、设计方向和实现假设。

## 技术栈

- React 19：视图与组件开发
- TypeScript 6：静态类型检查
- Vite 8：本地开发、热更新和生产构建
- ESLint 10：代码规范检查
- npm：依赖与脚本管理

## 启动步骤

### 环境要求

- Node.js `20.19+`、`22.13+` 或 `24+`
- npm（随 Node.js 安装）

### 本地开发

```bash
# 1. 安装依赖
npm install

# 2. 启动开发服务器
npm run dev
```

启动后访问终端中 Vite 输出的本地地址，默认通常为 `http://localhost:5173`。

### 质量检查与生产构建

```bash
# 运行 ESLint
npm run lint

# 执行 TypeScript 检查并构建生产文件
npm run build

# 在本地预览生产构建（需先完成 build）
npm run preview
```

## 请求层与状态管理的设计简述

### 当前实现

当前项目没有网络请求，也没有独立请求层。唯一的运行时状态是 `App.tsx` 中的计数器，使用 React `useState` 管理。对于这种只在单个组件内使用的临时 UI 状态，局部状态是最简单且足够的方案，无需提前引入全局状态库。

### 业务接入后的设计

- 在 `src/api/` 统一封装基础地址、请求头、超时、响应解析和错误映射，业务组件不直接拼接接口细节。
- 按业务域拆分请求模块，并通过 TypeScript 类型约束请求参数与响应数据。
- 加载中、失败、空数据和重试状态需要在页面上明确呈现；取消过期请求，避免旧响应覆盖新数据。
- 组件私有的交互状态继续使用 `useState`；需要跨层共享但更新频率不高的状态使用 Context。
- 服务端数据应由专门的数据请求/缓存方案管理；只有在出现明确的跨页面客户端状态需求时，才评估引入 Zustand、Redux Toolkit 等全局状态库。
- 登录令牌、权限和持久化策略必须在接口与安全要求明确后决定，不默认把敏感信息写入 `localStorage`。

## 开发过程中遇到的最难问题及解决过程

当前阶段最难的问题不是代码实现，而是在缺少业务需求、接口契约和 Part 5 原文的情况下，如何给出准确且可追踪的项目说明。

解决过程如下：

1. 逐项检查 `package.json`、应用入口、根组件、样式和 Git 历史，确认项目真实状态。
2. 将“已实现内容”和“建议的后续架构”分开描述，不把计划写成完成项。
3. 对无法从仓库验证的信息集中列出澄清问题，并为当前阶段写出显式假设。
4. 使用 `CHANGELOG.md` 和按改动提交的 Git commit 记录后续决策，需求变化时可以追踪和回滚。

## Part 5 澄清问题清单与实现假设

仓库中目前没有 Part 5 的原始题目、设计稿或验收标准。开始实现前需要确认：

1. Part 5 要解决的具体用户场景、必做功能和验收标准是什么？
2. 是否有设计稿、交互原型、指定页面尺寸或视觉规范？
3. 数据来自真实 API、Mock 服务还是本地静态数据？接口文档和示例响应在哪里？
4. 是否包含登录、角色、权限或令牌刷新流程？
5. 对加载、空数据、错误、重试、离线和请求超时分别有什么要求？
6. 状态是否需要跨页面共享、刷新后保留或在多个浏览器标签页之间同步？
7. 需要支持哪些浏览器、设备尺寸、语言和无障碍标准？
8. 是否要求自动化测试、覆盖率门槛、部署地址或特定提交格式？

在获得答复前，当前实现采用以下假设：

- 以现有 React + TypeScript + Vite 工程为开发基线，不额外更换框架。
- 当前只维护单页客户端应用，不假设存在后端、身份认证或持久化需求。
- 没有接口契约时不创建虚假的请求层；当前状态保持组件本地管理。
- Part 5 尚未实现，也不把起始模板视为 Part 5 的交付结果。
- 新需求采用移动端可用、语义化 HTML、清晰的加载/错误反馈作为默认质量基线。
