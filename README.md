# Gym 会员办卡订单管理后台

面向连锁健身房的会员办卡订单管理后台，用于登录后台、新建订单、查询和筛选订单、续卡、撤单，以及为财务导出可对账的订单数据。

当前已完成 React 18 + JavaScript 工程迁移、基础工具链配置、页面视觉 Demo、订单核心业务规则、可写内存 Mock 数据、Axios 请求层、登录与路由流程，以及订单列表、新建订单、续卡、撤单和 CSV 导出。完整需求基线见 [docs/REQUIREMENTS.md](./docs/REQUIREMENTS.md)。

## 请求层与状态管理设计简述

### 请求层

- 在 `src/api/` 创建统一 Axios 实例，通过环境变量配置 `baseURL`。
- 请求拦截器从登录状态中读取 token，注入 `Authorization: Bearer <token>`。
- 响应拦截器统一转换错误并调用 Ant Design Message 提示。
- 收到 401 时调用 Zustand store 的登出动作，清理本地 token，并导航到 `/login`。
- Mock 层保持异步接口形态，在内存中维护至少 30 条订单；查询、新建、续卡和撤单均通过同一 API 边界完成，使未来替换真实后端时页面改动最小。
- 当前 Mock 层包含 36 条初始订单，模块重新加载（即浏览器刷新）后恢复初始数据。

### 状态管理

- Zustand 只管理真正跨页面的客户端状态：token、当前用户名及登录/退出动作。
- 登录成功后将 mock token 和用户名保存到 `localStorage`；刷新页面时恢复登录状态与用户名。
- 未登录访问 `/orders`、`/orders/new` 时跳转 `/login`；已登录访问 `/login` 时跳转 `/orders`。
- 根路径根据登录状态跳转到 `/orders` 或 `/login`，退出和 401 均会清除登录状态。
- 列表查询条件、分页、跨页选择、弹窗和表单状态保留在订单页面，避免把短生命周期 UI 状态塞进全局 store。
- 订单号作为表格稳定选择标识；翻页时保留已选订单，切换状态 Tab、重新查询或重置条件时清空选择。
- 订单数据以 Mock API 为唯一数据源；写操作完成后重新查询，避免页面缓存与内存数据不一致。
- 续卡和撤单由 Mock API 先执行整批权限校验，再一次性更新内存数据；失败响应携带全部无效订单号，页面据此给出明确提示。
- 新建订单表单负责即时输入反馈，Mock API 负责最终数据校验；创建成功后写入同一内存订单仓库，返回列表重新查询即可看到新订单。
- CSV 导出重新使用当前已生效的筛选条件查询完整数据，在浏览器端执行导出权限过滤、格式化和文件下载，不依赖表格当前页或勾选状态。

## 订单状态约定

```text
待审核 → 待制卡 → 待寄卡 → 已完成 → 已到期
              └────────────→ 已取消
```

- “进行中”是筛选分组，包含待审核、待制卡、待寄卡。
- 续卡仅允许已到期订单；成功后累加年限并回到待审核。
- 撤单仅允许待制卡、待寄卡订单；成功后变为已取消。
- 默认按创建时间降序排列，最新订单显示在最前面。
- 新建订单的初始状态为待审核。
- 订单金额表示累计购卡费用；续卡成功后将本次续卡费用累加到原订单金额。
- 列表中的订单金额为空或 `null` 时显示 `--`；续卡累计时按原金额 0 元计算。

## 开发过程中遇到的最难问题及解决过程

订单支持批量续卡和批量撤单，但不同状态能做的操作不一样。批量操作还有个硬性要求：只要选中的订单里有一笔不符合条件，整批都不能执行。

为了避免列表组件又管 UI、又管业务判断、还管数据处理，我把订单状态相关的规则抽成了独立的纯函数，比如判断能不能续卡、能不能撤单、校验一批订单是否都符合条件、算续卡费用和折扣这些。

这些纯函数先用单元测试验证，再由 Mock 数据层统一调用。页面提交选中的订单号后，Mock API 会先找到全部目标订单，再按操作类型整批校验。

只要有一笔不符合条件，接口就返回全部无效订单号，并且不改任何订单；整批都通过了，才一次性更新所有目标订单。页面收到失败结果就展示无效订单号，操作成功就刷新列表和状态概览，并清空已选记录。

这样能保证批量操作的原子性，不会出现一部分成功、一部分被拦的情况，业务规则也和页面 UI 解耦了，后面维护和测试都轻松一些。

## Part 5：CSV 导出澄清问题

希望向业务方确认：

1. 导出文件需要使用什么格式？CSV、Excel（.xlsx）还是其他格式？
2. 哪些订单状态允许导出？哪些状态禁止导出？
3. 导出文件需要包含哪些字段？
4. “金额格式弄得好看一点”具体指什么？是否需要保留两位小数和千位分隔符？
5. 导出文件的名称有什么要求？
6. 是否需要记录导出操作，例如操作人和导出时间？

## Part 5：已确认的实现假设

根据“财务对账”和“部分状态不能随便导出”的需求，暂定以下实现规则：

1. 导出格式采用 CSV，不引入额外的 Excel 处理库。
2. 仅允许导出 已完成、已到期 的订单。
3. 导出字段包括：
   订单号
   会员姓名
   购卡年限
   订单金额
   订单状态
   创建时间
4. 金额统一保留两位小数，并使用千位分隔符，例如 1234567.8 导出为 1,234,567.80。
5. 文件名采用 健身房订单_YYYYMMDD_HHmmss.csv。
6. 当前测试环境暂不实现服务端权限校验和导出操作日志，导出权限仅在前端根据订单状态进行限制。

## 其他已确认实现规则

- 登录表单的账号和密码仍需非空；任意非空组合均登录成功。
- 已登录访问 `/login` 时跳转 `/orders`；根路径 `/` 根据登录状态跳转 `/orders` 或 `/login`。
- 新订单金额不享受折扣；只有单次续卡 5 年及以上按 8 折计费。
- 批量续卡弹窗同时展示单笔续卡费用和本次批量续卡总费用。
- 批量续卡包含无效订单时阻止整批操作，并列出所有无效订单号。
- 批量撤单包含无效订单时阻止整批操作，并列出所有无效订单号。
- 批量续卡和批量撤单支持跨分页保留勾选记录。
- 跨页选择仅在相同状态 Tab 和搜索条件下保留；切换 Tab 或执行新搜索时清空。
- 已到期订单由 Mock 初始数据提供，不实现自动到期。
- 不提供手动订单状态推进功能。
- 页面适配常见桌面和平板宽度。
- 使用 Vitest 为金额计算、状态权限、筛选和 CSV 转义补充单元测试。
- 手机号仅支持中国大陆 11 位号码，正则为 `/^1[3-9]\d{9}$/`。
